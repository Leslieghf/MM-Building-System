# Static Prop Asset Candidates — 2026-10-31

## Current classification

Mad Max has at least two distinct ways scenery can enter the world:

1. World/map scenery may be authored into streamed region or chunk data. We have not yet inspected those map formats, so this remains an open possibility rather than a confirmed statement about every static object.
2. The game also has a game-owned spawn system that loads an exported entity file (`.ee`) and receives a world transform. The community `MadMaxSpawner` calls `SSpawnInstanceInfo::SetEntityFile`, appends `.ee`, sets the spawn descriptor, and passes it with a transform to `SpawnSystemSpawn` from the game-event path. This is direct evidence that a spawnable entity need not be a baked map placement; it is not evidence that every environment prop has its own standalone entity file.

### Local archive inspection

The installed TAB tables store 32-bit keys that match Mad Max `HashString` applied to the **exact basename including `.ee`**; the call itself does not lowercase its input. The public Mad Max source mirror's `ALib/Hash.cpp` defines `HashString` as Bob Jenkins `hashlittle` with seed 0. This exact implementation was independently reproduced and matches catalog entries: `a00_vehicle_empty_buggy.ee` -> `0x58904414` in `game31.tab`, and `a01_static_wreck_0002.ee` -> `0x0816F6CC` in `game36.tab`. The stockpile `.ee` is `0x0E061D50` in `game33.tab`. For known names, this permits targeted archive lookup even without a reconstructed path list; broad archive browsing still benefits from Gibbed's `.filelist`/`.dirlist` data.

Two candidates were extracted to temporary memory for local inspection only; no game files were changed:

- `a01_wasteland_lootbox_roadkill_normal.ee` is a version-2 `SARC` archive with 70 entries. It includes one `.epe` definition (22,409 bytes), collection animations, loot and opportunity-vision graph scripts, multiple scrap models, collision resources, sounds, and localized string lookups. Its `.epe` names `CRigidObject`, interaction/trigger components, a sound emitter, and loot systems. This is an interactable loot composition, not a neutral static prop.
- `a01_static_wreck_0006_birds.ee` is a version-2 `SARC` archive with 302 entries. Its `.epe` definition (346,420 bytes) names `CRigidObject`, `CDestructibleObject`, `CShapeTrigger`, `CSkeletalAnimatedObject`, interaction components, and numerous wreck, corpse, bird, and scrap resources. Despite `static_wreck` in the asset key, it is a complex encounter/world composition rather than a clean one-object prop target.

The strongest current candidate is `editor/entities/a00/propsenc/expentity/a00_propsenc_projects_stockpile_small_01`. Its `.ee` SARC contains 37 entries and one 1,650-byte `.epe`; that definition names one `CRigidObject` using `models/a00/propsenc/projects/a00_propsenc_projects_stockpile_small.model_xml` and `models/a00/propsenc/projects/a00_propsenc_projects_stockpile_small_col.pfx`, plus `CFadeComponent` and `CGraphScriptGameObject` referencing opportunity-vision and persistence visibility graphs. The bundle contains a corresponding 5,268-byte `.pfxc` collision resource. That resource begins with a Havok 2013.2.0-r1 packfile header and names `hkpRigidBody`, `hkpConvexVerticesShape`, `hkpShapeInfo`, `hkpPhysicsData`, and `hkpPhysicsSystem` in its serialization metadata. This establishes that the entity package supplies a real Havok collision resource, but its rigid-body motion type and whether the object is fixed/static remain unverified. Its graph/fade components also mean it carries authored behavior; treat it as a candidate for a controlled spawn test, not as a neutral prop.

Additional lightweight catalog candidates were checked by archive key and their `.epe` dependency strings. The armory bundle (1,771,928 bytes) has one `CRigidObject`, one `.pfxc`, a wheel submodel reference, and the same graph/fade behavior. Cleanup crew (2,345,160 bytes) and super fuel (1,276,912 bytes) each have one `CRigidObject`, one `.pfxc`, and the same behavior set. Maggot farm (512,176 bytes) is smaller but adds `CCreationTrigger`, `CEffectPointEmitter`, `Cfx_env_flies`, and `Cmaggots`, so it is behaviorally less suitable. These definitions all reference `.model_xml` and `.pfx` logical paths, while the corresponding SARC packages contain `.rbs`, `.rbn`, `.lod`, and `.pfxc` resources rather than a `.model_xml` entry. An archive-wide exact `HashString` lookup did not find the stockpile `.model_xml` by either its basename or its full referenced path; the reference therefore should be treated as a model/resource key, not assumed to be a standalone archived file.

The current community spawner source was fetched at commit `4c9af72cd7cd4fd8c40f24f90a4498a66850dae6`. Its `spawnermenu.cpp` confirms exact entity keys for the roadside wrecks, loot compositions, and projects. It also supplies the exact paths for the inspected project bundles: `editor/entities/a00/propsenc/expentity/a00_propsenc_projects_armory_01`, `...cleanup_crew_01`, `...super_fuel_01`, and `...maggot_farm_01`. The lootbox key is under `encounters/exported/loot/`, not `encounters/exported/wasteland/`; the catalog and this note use the source path. The generated `assets/catalog/community-candidates.json` contains 456 deduplicated names from the source's `empty_vehicle` and `all_entity` arrays. All imported rows remain `name_only` and `blocked`; this is a discovery list, not a list of verified archive entries or safe spawn calls.

These container observations support the user's map/chunk concern in a qualified way: the spawner catalog's `.ee` resources are not necessarily individual renderable objects; at least these examples package many files and multiple gameplay components. This does **not** establish whether ordinary map scenery is baked into region/chunk data.

## Runtime type evidence: rigid props and destructible variants

Ghidra's MSVC RTTI for `CRigidObject` confirms a concrete inheritance chain: `CRigidObject` derives from `CPhysicsGameObject` and `IPfxGameObject`, then through `CGameObject`/`CRtti`; it also implements the game event handler and PFX/Havok activation-listener interfaces. This is direct executable type metadata, not a guessed label. The image contains creator RTTI for `CGameObjectCreator<CRigidObject>`, `CGameObjectCreator<CDestructibleObject>`, and `CGameObjectCreator<CDestructibleObjectKeyframed>`, plus separate `CScaledRigidObject` and `CAnimatedRigidObject` classes. That suggests object composition and creator registration are central to entity instantiation; the type names alone do not tell us which asset becomes static or how to call a creator.

The pinned SDK declares `CPhysicsGameObject::SetKeyframedMotionState(bool)` and `SetNextKeyframeTransform(...)`, as well as `GetPhysicsAABB`, collision callbacks, material overrides, and water/buoyancy hooks. `CRigidObject`'s RTTI proves it inherits that physics surface. This makes “spawn a game-owned rigid object, then configure keyframed motion” a plausible future line of research, but no concrete virtual slot, object readiness precondition, or safe call context has been established. No such setter is called from the current Rust bridge.

### First visual spawn probe: small stockpile composition

The first in-game probe uses `editor/entities/a00/propsenc/expentity/a00_propsenc_projects_stockpile_small_01`, because its archive is small and its `.epe` defines one `CRigidObject` with an explicit Havok collision resource. It is deliberately described as a **rigid prop candidate**, not yet as a verified fixed/static body: the `.pfxc` contains `hkpRigidBody` metadata, but its motion type has not been decoded. The Rust overlay's one-shot spawn control now takes the latest completed `reticle_ray` hit position from the copied game snapshot, adds 0.5 units on world-up, preserves Max's current orientation, and submits this fixed key. The action remains unavailable until a hit exists. The probe has no removal action; submission still does not prove the loader produced an instance. The visible object and whether the existing world query can hit its collision are the manual acceptance signals. A failed attempt should leave the game untouched beyond that one spawn request.

## `settings/worlddecorations.bin`: an authored object-composition resource

Ghidra contains the exact resource path string `settings/worlddecorations.bin` at `0x1412B1A58`, plus RTTI for `CWorldDecorationCache` and `CWorldDecorationResource` and creator records for both. The exact `HashString` of the basename is `0x2AB9CD40`; scanning the installed TAB files locates it in `game13.tab` at archive offset `0x1DDEE800` (853 compressed bytes, 1,871 decompressed bytes). This pins a real, very small decoration resource in the installed archive and independently confirms that the executable has decoration-cache/resource types. It does **not** yet link this exact path to those classes: the path string has no Ghidra code/data xrefs, and the cache load function remains untraced. We have not established whether the file describes map placements or reusable decoration compositions.

The 1,871-byte file parses completely as a `RawPropertyContainerFile` using Gibbed's documented node/property/tag structure. It contains six nested nodes. One parent node has two `CRigidObject` definitions that both reference `models/a00/props/barrel01/a00_pr_barrel01_red.model_xml` and its matching `.pfx` collision path; their 4x3 local transforms are identity at the origin and identity translated by 2 units on X. The same parent contains a `CDynamicLightObject` child with its own local transform. A sibling is a `CStaticDecalObject` with four texture references and a local transform translated by 0.2 units on X. This is strong evidence for authored *small object groups* represented as game-object components with model/collision/material resources and relative transforms. It is not yet evidence that these definitions are directly spawnable or that their transforms are world coordinates.

This identifies a third *candidate* content route alongside entity `.ee` bundles and save-backed authored-target state: a compact decoration composition/resource format, with matching decoration-cache/resource types in the executable. The file-to-cache link is still a hypothesis. Next RE should trace the cache/resource registration and load path and determine how this format becomes live `CGameObject`s. If it can be instantiated through a game-owned creation path, it may be a better first static-object target than the larger `.propsenc` project bundles. Do not call the resource creator or mutate the file until that runtime lifecycle is mapped.

### Static follow-up: names and executable references

Gibbed's property-field `HashJenkins` and the game's archive `HashString` use the same Jenkins 32-bit byte-hash algorithm for the same bytes (seed zero, initial state `0xDEADBEEF + input length`, little-endian byte packing, and the same final mix). The practical distinction is input preparation: Gibbed's archive file-list loader lowercases each basename before hashing, while `RawPropertyContainerFile` hashes the serialized ASCII property name as written. Thus casing/normalization matters even though the hash algorithm does not differ. Class `.namelist` files are the intended reverse-lookup mechanism. The public repository currently contains only six class namelists (`CEventTrigger`, `CGraphScriptGameObject`, `CLogBookMessage`, `CRestartPoint`, `CTimeTrigger`, and `SEventTriggerComponent`), so it does not provide a ready-made `CRigidObject` field dictionary; test candidate field names with exact serialized casing and do not assume the community `.namelist` coverage is complete.

The `settings/worlddecorations.bin` string itself has zero xrefs in the current Ghidra database. Separately, the `CWorldDecorationCache` type descriptor has RTTI references from a complete-object locator and base-class descriptor, and the locator is referenced by a vtable metadata pointer. Its MSVC hierarchy has exactly three entries: `CWorldDecorationCache`, `IAppSystem@Base`, and `CAvaSingle<CWorldDecorationCache>`. This confirms it is an app-system singleton, not just an incidental resource type. The six qwords immediately after that vtable metadata point into `.xpdata`, a non-executable Ghidra memory block. This is not enough to call them native methods or infer the cache lifecycle: the addresses do not decompile as ordinary native functions. It is a useful boundary clue, because the class dispatch metadata leads into the game's `.xpdata` representation; the exact meaning (bytecode, data, runtime-generated code, or section-protection mismatch) remains open. Avoid renaming these targets as normal C++ methods until that representation is understood.

The same RTTI/vtable survey found a distinct map-streaming family: `CGameZoneMapStreamPatch`, `CTerrainMapStreamPatchBase`, and `CTerrainDataStreamPatch` inherit through `CStreamPatchGame` and `CStreamPatchBase`; `CTerrainTextureStreamPatchGame` has the same bases. Their RTTI-associated table addresses are respectively `0x14131BDC0`, `0x14131BEF0`, `0x14131BE88`, and `0x14131C098`. Across these tables, slots 1, 2, and 4 point to the same three addresses (`0x142434C70`, `0x142434CA0`, `0x142434D50`), consistent with shared base-class virtuals; slot semantics are unknown. `CTerrainPatchReader` derives from `CPatchReader` and has its own table at `0x14131F138`. `CLandscapeManager` has RTTI bases `CLandscapeManager`, `CAvaSingle<CLandscapeManager>`, and `IAppSystem@Base`, with its table at `0x14131F100`. These are concrete named leads for map streaming, but their table targets mostly land in `.xpdata` and remain one-byte Ghidra stubs or unrecognized addresses. No direct `.fl.mdic`-to-class link is established, so do not yet claim these classes parse the observed MDIC format.

## Separate avenue: persistent world-resource state for authored targets

The public [MadMax Savegame Editor Project](https://github.com/Rick-Thompson/MadMax_Savegame_Editor_Project) has a verified save-edit path for restoring and clearing supported world-object targets (including scarecrows). Its `mmworld.py` edits the save's economy-resource roster and related map markers; this is a load-time/persistent gameplay-state mechanism, **not** a runtime `CGameObject` deletion API and not arbitrary removal of scenery. It can be useful for a separate “reset/clear supported target” feature after reload, but it cannot currently remove the specific object under a raycast or arbitrary camp prop.

Important version/caveat from that project's own current documentation: the roster field previously described as a destroyed/intact flag was corrected to `LastAmount`, a resource quantity. Threat objects only look boolean because their profile capacity is 1; the proper restored value is the profile's `StartAmountMax`, not a universal literal `1.0`. The same project documents type 45 as a confirmed scarecrow profile and types 45–48 as the four scarecrow size groups, with object counts cross-checked against shipped `scNNNN` entity names and `global/tracked_objects.bl`. This is an excellent source of reproducible object-state mappings, but we should follow its corrected economy interpretation rather than copy the older `mmworld.py` assumptions blindly.

That result sharpens the architecture into three independent capabilities:

1. **Spawn mod-owned shipped entity:** use the game spawn system; still gated on asset and ownership/completion verification.
2. **Reset or clear supported authored targets:** edit documented per-playthrough resource state and markers, then reload; this is save-backed and limited to enumerated target types.
3. **Delete arbitrary map-authored object:** requires live object identity plus a confirmed game removal route; still unsolved.

The save-edit path should not be described as the arbitrary map-object-removal adapter in the approved runtime design. It is a separate offline/persistent adapter with different timing and state semantics.

## What the SDK says about the spawn lifecycle

The pinned community SDK declaration in `gigaHours/mm_sdk/game/spawnsystem.h` provides these facts:

- `SpawnSystemGetNewSpawnId` returns a `CHashString&` through the SDK's hidden-result argument convention.
- `SpawnSystemSpawn(SSpawnInstanceInfo*, CMatrix*)` returns `size_t`; the known spawner ignores the return value.
- `SpawnSystemDespawn(CHashString const& id)` accepts a spawn ID, not a host request ID or a raw entity pointer.
- `CSpawnedEntityHandler` holds spawned-entity records, pending spawn and delete queues, and last-frame arrays for spawned, despawned, and failed hashes.
- `CSpawnedEntity` has a named entity ID and comments indicating that its spawned `CGameObject` collection was not fully reversed by the SDK authors.

### Additional ABI and layout details

Inspection of the pinned SDK's `hookmgr.h`, `core/hash.h`, `std.h`, and the full `game/spawnsystem.h` adds these details:

- SDK `SMETHOD` expands to `HookMgr::Call<Return>(address, arguments...)`, and `HookMgr::Call` casts the address to an ordinary function pointer with those exact arguments. It does not add an implicit `this` pointer.
- `SpawnSystemGetNewSpawnId` is declared as `CHashString& SpawnSystemGetNewSpawnId(CHashString const& result)` and called with `&result`. This is consistent with caller-provided result storage: the native routine receives a pointer to a four-byte `CHashString`, writes the generated hash there, and returns a reference to that same object. A Rust candidate is therefore `unsafe extern "system" fn(*mut u32) -> *mut u32`; this remains an ABI inference until runtime-validated. A wrapper should initialize the word and reject a returned pointer that differs from the supplied storage.
- The SDK's `mm::std::vector<T>` is three pointers plus eight bytes of padding, aligned to eight, so its declared size is 0x20 on the target. In `CSpawnedEntityHandler`, the six vectors consequently begin at offsets `0x50`, `0x70`, `0x90`, `0xB0`, `0xD0`, and `0xF0`: spawned entities, spawn queue, delete queue, spawned-last-frame, despawned-last-frame, and failed-last-frame respectively. This is header-derived layout, not yet validated against a live handler instance.
- The SDK directly dereferences the spawn-handler singleton at `0x14171B678` in its older/GOG path. The project's build pair maps that same address for GOG and `0x1417FEE78` for Steam; this matches the existing Steam executable mapping. Do not use the GOG-only literal when reading the user's Steam process.
- `CSpawnedEntity::m_EntityId` is described by the SDK's accessor as the hash used to find a spawned record, while `SSpawnInstanceInfo::m_SpawnId` is the queue item's ID. The SDK comments show that the relationship between the two is not a simple confirmed identity: its live spawned-record lookup compares `m_EntityId`, while the separate queue lookup compares `m_SpawnId`. Correlation must be observed, not assumed.
- The SDK's `CGameObject` declaration exposes transform/hierarchy operations and object IDs, but no general remove/destroy entry point. That does not prove the executable lacks one; it means the public SDK offers no independently documented route for deleting an arbitrary map-authored object. The only documented removal route found so far is spawn-system despawn by a hash ID.

This means the Rust request counter must **not** be treated as a native spawn identity. The SDK allocator has a plausible caller-storage ABI, but it has not been exercised or validated in a live run. Cleanup also needs evidence that the matching despawn route removes precisely that spawned record.

## Current Rust boundary

- `SpawnIntentEnvelope` carries a host request ID, asset key, and copied matrix.
- `apply_spawn_intent` asks the SDK allocator for a native `CHashString` and assigns it to both spawn identity fields. Its `NativeCallSubmitted` result means only that the native call returned; it is not a confirmed spawn.
- Host request IDs remain Rust/UI correlation keys and are never passed to Mad Max as spawn identities.
- The game callback copies bounded `spawned`, `despawned`, and `failed` ID arrays from the SDK-described handler vectors, then correlates those values with native IDs returned by the allocator. The UI offers removal only after the matching ID appears in the game's spawned list.
- Removal requests carry only the host request ID through UI transport. The game runtime resolves it to the stored native ID and calls `SpawnSystemDespawn` on the accepted game callback. A submitted despawn stays pending until the handler reports that native ID as despawned. The allocator, vector layout, and despawn call still need a live test.
- The spawn menu performs its own camera-origin `PlayerAim` query while Q is held. It does not depend on the optional `reticle_ray` Rhai script; that script remains an independent diagnostic.
- No entity file list or extracted `.ee` file is present under the project, game install, `MadMaxModding`, or the user's profile search. The Gibbed project manager expects configured project XML plus `projects/<name>/lists/files/*.filelist` data; its `RebuildFileLists` tool can index archives once those project lists are available, but they are not bundled in the source repository. `dotnet` is not available in the current shell, and Mad Max is open, so this pass has not run an archive rebuild tool or installed a new plugin.

## Verified streamed landscape placement data: one `.fl` patch

The installed `game4` archive entry for `a01_patch_12-13_32-33.fl` decompresses to a version-2 SARC containing one file, `locations/a01/landscape_locations/a01_patch_12-13_32-33.fl.mdic` (5,192 bytes). The MDIC header contains version `12`, three model-path strings, a count of `46`, and a string-table byte length of `192`. The three paths, in table order, are:

1. `models/a01/environment/rock/set01/a01_env_rock_set01_big01.lod`
2. `models/a01/environment/rock/set01/a01_env_rock_set01_ledge02.lod`
3. `models/a01/environment/rock/set01/a01_env_rock_set01_flat01.lod`

Starting at offset `0xE0`, the payload contains exactly 46 consecutive 64-byte matrices. All 46 decode as finite, orthonormal transforms with positive determinant approximately `1.0` and homogeneous component `1.0`; translation is at matrix elements 12–14. A following 92-byte table contains 46 little-endian `u16` values, each in the range 0–2, matching the three model paths. Interpreting those as model-path indices yields 5 placements for index 0, 40 for index 1, and 1 for index 2. Their translations span X `[-9656.38, -9255.30]`, Y `[373.89, 504.05]`, and Z `[-20.23, 893.38]` in the file's game-space coordinates.

This is direct evidence that at least one ordinary landscape patch stores reusable model references plus per-instance world transforms, rather than only a single baked render mesh. It provides a concrete static-placement data format to study for the user's building goal. It does **not** yet establish that the game accepts mod-created `.fl` data, that these entries carry Havok collision, or that runtime object deletion follows the same route. After the transform and model-index arrays, the file has a 46-entry `u16` table uniformly set to `0x00FF`, followed by a 1,840-byte region (exactly 46 × 40 bytes). The next byte-level pass below confirms that this final region is populated and structured, but does not yet identify its game-level meaning. Treat the 3-path/46-transform/index interpretation as a strong structural mapping, not a complete MDIC specification.

The surrounding `world.bin` manifest separately names this exact `.fl` resource under the landscape patch path and associates that location with spatial bounds. This ties the placement asset to a streamed map location, reinforcing the user's region/chunk intuition. It does not imply every class of map prop uses `.fl`.

### Evidence and source boundary

- `game4.tab` resolves the lower-case basename hash `0xDC6BEFE5` to archive offset `0x1D706000`, compressed size 3,240, decompressed size 5,288. The extracted SARC contains the 5,192-byte MDIC payload at its sole entry.
- The 46 matrices were checked numerically for basis lengths, pairwise orthogonality, and homogeneous `w`; all pass with zero error at the observed single-precision values.
- The separate `u16` table has 46 values and all values reference one of the three path-table positions. Asset-to-index identity is inferred from that alignment and range.
- A second nearby patch, `a01_patch_12-13_30-31.fl`, uses the same three rock paths and has 68 transforms, 68 valid indices with counts 2 / 64 / 2, 68 `0x00FF` auxiliary values, and exactly `68 * 40` remaining bytes. All 68 transforms pass the same determinant, orthogonality, and homogeneous-component checks. Together, these three independent patch files support the array layout and model-index mapping across instance counts 46, 68, and 162.
- An independent neighboring resource, `a01_patch_12-13_34-35.fl`, validates the same layout: MDIC version 12, 10 path strings, 162 instances, a 162-matrix array, 162 `u16` model indices (all 0–9), and a 162-entry `u16` array uniformly set to `0x00FF`. The final 6,480 bytes are exactly `162 * 40`. All 162 matrices also pass the basis-length, orthogonality, determinant, and homogeneous-component checks. Repeating the layout at a different count and path-table size makes the array interpretation much stronger than the original single-file fit.
- The MDIC arrays start after the 32-byte header plus the declared model-path string-table byte count, not at a fixed absolute offset: `0xE0` for the 46-entry / 192-byte-string-table patch, `0xF0` for the 68-entry / 208-byte-string-table patch, and `0x2B0` for the 162-entry / 656-byte-string-table patch. From there, matrix array (`64 * count`), model-index table (`2 * count`), `0x00FF` table (`2 * count`), and final region (`40 * count`) end exactly at the MDIC boundary in all three files.
- The final 40-byte records can be viewed as ten little-endian `f32` slots apiece: none of the 2,760 slots across the three samples is NaN or infinity. Per patch, rows divide into all-zero / all-`-1` / ten other finite values / mixed rows as follows: 46-entry patch `13 / 4 / 27 / 2`, 68-entry patch `20 / 6 / 40 / 2`, and 162-entry patch `48 / 15 / 97 / 2`. Many non-sentinel values look coordinate-like and are on the same scale as the map positions (combined range about `-10,681.53` to `1,901.27`), but their grouping and semantics are unresolved; do not name this as bounds, collision data, or vertices yet.
- Gibbed's source documents the archive-table lookup and SARC v2 container, but does not document this MDIC payload schema. The MDIC field names above are therefore observations/inferences from the shipped bytes, not copied SDK declarations.

A second RTTI pass used the decorated MSVC names (for example, `.?AVCMapStreamer@@`) rather than nearby bare class-name strings. ## `.xpdata` startup path and executable-section handling

A direct read of the PE headers resolves an important naming ambiguity: this executable has a separate `.pdata`-named section beginning at RVA `0x01A0C000`, and the PE Exception Table data-directory entry points to that RVA with size `0x00125580` (the section's virtual size is `0x00125600`). At 12 bytes per x64 `RUNTIME_FUNCTION` record, the directory contains 100,128 entries. `.xpdata` is a distinct section at RVA `0x01B38000`, about 69.3 MiB long. Its on-disk characteristics are `0x40000040` (`IMAGE_SCN_CNT_INITIALIZED_DATA | IMAGE_SCN_MEM_READ`), not an exception-table designation and not executable in the file's section flags. The name `.xpdata` is not a standard PE-format promise of `.pdata`/`.xdata` semantics. Microsoft documents `.pdata` as the function-table section used by x64 exception handling; in this binary that role is separately accounted for by the Exception Table directory. Therefore the Google summary's claim that Mad Max's `.xpdata` is merged unwind data is contradicted by the PE headers.

Scanning all 100,128 exception-directory records shows every `BeginAddress` falls inside `.xpdata`. This is strong evidence that `.xpdata` contains the function ranges the OS unwind table describes, despite the section's read-only data flag. The creator vtable destinations `0x14209D9E0`, `0x14207C160`, and `0x14208FD80` each exactly match a `BeginAddress` in that table, with respective end RVAs `0x0209DA56`, `0x0207C626`, and `0x0208FE0F` and unwind RVAs `0x015ECDE4`, `0x015E8368`, and `0x015EAF24`. Thus these are not merely arbitrary data pointers: the PE's unwind metadata classifies them as function ranges. That still does not prove their on-disk bytes are plaintext machine code or show whether/how they are transformed before execution. The startup callback at `0x1432C1D4F` and the two one-byte auto-function stubs at `0x1432BB3F0`/`0x1432A8630` are not exact `BeginAddress` entries in this table, so do not generalize the table coverage to every code-looking address in `.xpdata`.

A startup-path pass established that the PE section flags shown by Ghidra are not the runtime protection contract. The entry function at `0x141B36728` first calls `DecryptStartupImageBufferAes256Cbc` on `.xpdata` from `0x141B38000` for `0x22BC4` bytes, then calls `InitializeProtectedRuntime` at `0x141B35151`. The first pointer passed by the entry is the 32-byte AES key at `0x141B366E8`; the second is the CBC IV at `0x141B36708`. The decryptor processes `length / 16` blocks in place, applies 14-round AES-256 inverse transforms, and XOR-chains each plaintext block with the prior ciphertext/IV. Because `0x22BC4` has a four-byte remainder, only the first `0x22BC0` bytes are covered by its block loop; the final four bytes are not transformed by that loop. A read-only AES/CBC probe using those key and IV bytes reduces the first 64 KiB sample's byte entropy from about 7.997 bits/byte to 7.798, but the result is still opaque rather than recognizable native code or a known data structure. This validates the cipher/mode interpretation more strongly than the disassembly alone, while leaving the decrypted prefix's purpose unresolved.

`InitializeProtectedRuntime` calls `InitializeImageSectionsAndInvokeEntryCallback` at `0x141B35000`, passing callback address `0x1432C1D4F`. That bootstrap walks the PE section table, clears `IMAGE_SCN_MEM_WRITE` in the in-memory section characteristics, calls `VirtualProtect` on each section range with protection `0x40` (`PAGE_EXECUTE_READWRITE`), then invokes the callback. Thus `.xpdata` being marked non-executable in Ghidra does not mean its code is non-executable at runtime.

The imported `VirtualProtect` has only two static call sites in the executable: this per-section startup permission change and the AES startup decryptor, which temporarily requests protection `4` (`PAGE_READWRITE`) for its target buffer and then restores the prior protection. This gives no static evidence of a repeated `VirtualProtect`-based, per-block decrypt/execute cycle. It cannot rule out a custom permission path or decryption into memory that is already writable/executable; after the bootstrap, all image sections have been made RWX anyway.

The callback address `0x1432C1D4F` is valid x64 code inside `.xpdata`; its body calls `0x1432BB3F0` and `0x1432A8630`. Follow-up disassembly shows these are not simply undecodable bytes at their entries: both begin with coherent x64 setup instructions, reserve large stack frames (`0x62B0` and `0x5A88` bytes respectively), then jump into distant `.xpdata` regions. The first target at `0x145B1E769` immediately jumps again to `0x145A5A516`; the second target at `0x145B8EEEA` immediately jumps again to `0x145D3EE2C`. Other bytes around these branch destinations decode inconsistently as instructions, so linear disassembly is not a trustworthy model of the region. This confirms deliberate control-flow redirection/opaque code, but does not identify the mechanism or prove whether the eventual body is native code, interpreted bytecode, or a mixture.

The callback's first call passes two adjacent byte ranges immediately before the callback: `0x1432C1CDD` with length `0x3C`, and `0x1432C1D19` with length `0x36`. Their bytes are high-entropy-looking in the on-disk image. This is a concrete startup operation over two small payloads, but the callee's signature/semantics are not yet established; do not label it decryption based on the opaque inputs alone. The callback then calls `0x1432A8630` with no explicit arguments.

The helper calls immediately before the large stack allocations (`0x1432B6030` and `0x14328CFC0`) were decompiled separately. Both use the requested stack size from RAX, consult the thread stack boundary via `GS:[0x10]`, and touch pages at 0x1000-byte intervals. This is consistent with a Windows x64 large-stack probe (`__chkstk`-style behavior), not a decryption routine. The large frame setup therefore appears to be ordinary stack-management scaffolding around the opaque redirected bodies; it does not itself explain their code representation.

An initial `.xtext` sample (first 0x200 bytes) shows repeated compact binary records rather than obvious plaintext or ordinary x64 code. Several leading groups pair small integers with high-bit-tagged values such as `0x80000040`; later groups contain values such as `0x00000409` and small offsets such as `0x2E0`. The field meanings, pointer/tag encoding, and relationship to `.xpdata` remain unknown. A raw scan also finds a standard-looking version-information string block near the end of `.xtext` (`VS_VERSION_INFO`, `StringFileInfo`, `CompanyName`, `AvalancheStudios`, `FileDescription`, `MadMax Game`, `OriginalFilename`, and version `1.0.3.0`). This confirms `.xtext` includes human-readable metadata as well as the earlier binary records; it does not identify those records' format or make the section an exception table.

The `CRoadDecorationCreator` table at `0x1412B18B0` has initial targets `0x14209D9E0`, `0x14207C160`, and `0x14208FD80`. Their raw bytes are high-entropy-looking and they lie roughly 5.2–5.4 MiB into `.xpdata`, far beyond the startup decryptor's 142 KiB prefix. A probe applying the startup AES key to a target-sized sample with its preceding ciphertext block as CBC state did not yield an obvious native-code prologue; this only rejects that simple same-key/continuous-CBC interpretation, not other transforms or per-object keys. These remain opaque dispatch targets; do not treat their raw bytes as a valid function body or assign virtual-method names/signatures yet. The `.xpdata` block is about 69.3 MiB; the adjacent `.xtext` block is about 210 KiB and starts with structured-looking tables, but its format is also unresolved.

An external reverse-engineering pattern catalog groups the section-name family `.xcode`/`.xtext`/`.xpdata` with encrypted-VM runtime patterns. Its detailed playbook targets Unity IL2CPP binaries, so it is **not** evidence that Mad Max uses that specific protector or that its recipe applies here. It is a useful cross-title lead only: check future candidate binaries for the same section family and compare their bootstrap/decryption structure before borrowing any decoder assumptions. [Pattern catalog/playbook](https://github.com/Heretek-AI/heretek-claude-harness/blob/main/plugins/re-ai/tools/RE-BREAKER/docs/PLAYBOOKS/encrypted-vm-bytecode-interpreter-pattern-a.md).

Ghidra's bootstrap and AES helper names now reflect the directly observed behavior (including `InitializeImageSectionsAndInvokeEntryCallback`, `DecryptStartupImageBufferAes256Cbc`, and the AES inverse-transform helpers). Bookmarks were added at the entry path, section-protection bootstrap, callback, and one opaque creator slot. No live process was read or changed for this pass.

The community `XvmDisassemble` path does not directly accept these targets: its entry point reads an ADF container, locates the instance named `module`, then deserializes an `XvmModule`. A small static probe interpreted 64 16-bit words at several vtable target addresses using Gibbed's packed-XVM opcode rule; it found undefined opcode IDs and inconsistent `Ret` positions. That rejects the simple “these pointers directly address ordinary XVM instruction arrays” theory, but cannot rule out a wrapper, different encoding, or another `.xpdata` representation.

### Live-process code comparison

While Mad Max was running at Pink Eye's Fortress, a strictly read-only `ReadProcessMemory` comparison was made against the same image RVAs in Ghidra's on-disk program. No breakpoint, suspend, write, or other process modification was used. At `.xpdata` RVA `0x01B38010` (inside the known AES-covered startup prefix), the file begins `3B 62 FF 29 33 9B C8 A8 ...`, while live memory begins `48 89 54 24 10 53 48 83 EC 20 ...`, a coherent x64 prologue. The `.pdata` record identifies it as a function from RVA `0x01B38010` through `0x01B3803B`; this maps the known startup AES operation to at least one actual function body, rather than unknown data.

More importantly, the `CRoadDecorationCreator` function at RVA `0x0209D9E0`, far beyond the AES prefix, is also transformed: file bytes begin `97 C9 26 24 4E CC D5 81 ...`, while live memory begins `48 89 4C 24 08 57 48 83 EC 30 ...`, a coherent x64 function prologue. Nine additional `.pdata` function starts sampled across the table from RVA `0x01B380A0` through `0x0328BA30` all differed from their file bytes and began with plausible native x64 instruction sequences in the live process. This establishes that a second runtime transformation makes function bodies throughout the `.pdata`-covered `.xpdata` range readable/executable in the running image; the one known AES pass does not explain the distant creator target or the other samples.

The live samples do **not** establish whether that second transformation eagerly decodes all code during startup or lazily decodes functions when first needed. The startup callback's two opaque routines are called before normal game execution and remain prime candidates, but their bodies are still hidden behind branch chains. A same-run read can prove file-vs-runtime transformation, not the time at which each sampled function changed. The useful next discriminator is a before/after-startup sample or a runtime trace around the callback's redirected bodies; no such timing evidence has been captured yet.

### Unchanged bootstrap and dispatch bytes in the live image

The same read-only comparison also sampled the startup callback (`0x1432C1D4F`, RVA `0x032C1D4F`), its two helper entries (`0x1432BB3F0`, RVA `0x032BB3F0`; and `0x1432A8630`, RVA `0x032A8630`), and several destinations in their jump chains. At each of those locations, the live bytes matched the on-disk image exactly. Additional unchanged jump-chain samples were RVAs `0x05A4049B`, `0x032B596B`, `0x05A3A74C`, and `0x05A4A484`. This contrasts with the sampled `.pdata`-listed function starts, whose live bytes differ from disk and decode as plausible x64 code.

The evidence therefore supports a **mixed representation**: sampled registered function bodies are transformed in memory, while the sampled bootstrap/dispatch islands remain unchanged. It does not prove those unchanged bytes are bytecode; they may be opaque native control-flow material or another kind of dispatcher. Nor does it settle whether function transformation is eager or demand-driven. The result argues against a simple model where one startup AES pass decrypts all of `.xpdata` uniformly. Any claim about the transform mechanism or timing still needs a targeted before/after-startup capture or a well-scoped runtime trace.

### Vtable pointers versus transformed target bodies

To test whether the runtime rewrites vtables before a virtual call, the first 64 bytes of the `CRoadDecorationCreator` table at VA `0x1412B18B0` were read from the running process and compared with the on-disk Ghidra image. They match byte-for-byte. The first three qwords still point to `0x14209D9E0`, `0x14207C160`, and `0x14208FD80`. In the same process, those target addresses contain plausible native x64 prologues; for example, `0x14209D9E0` starts `48 89 4C 24 08 57 48 83 EC 30`, while its on-disk bytes start `97 C9 26 24 4E CC D5 81`.

This is direct evidence that **this observed vtable was not rewritten** and that at least one of its code targets is transformed in place at the same virtual address. It supports the possibility of code decoding before execution, but does not tell us whether decoding was eager at startup, performed on first use and retained, or repeated around calls. It also does not prove all Mad Max vtables behave identically. The outer startup call uses the normal Windows x64 register argument positions (RCX, RDX, R8, R9); the opaque jump islands may implement internal control-flow obfuscation, but current evidence does not justify calling this a custom function ABI.

### Startup callback chain: first control-flow layer

The callback is a small, ordinary x64 wrapper: it places pointers `0x1432C1CDD` and `0x1432C1D19` in RCX/R8, places lengths `0x3C` and `0x36` in RDX/R9, calls `0x1432BB3F0`, then calls `0x1432A8630`. The first helper saves those four incoming values in the Windows x64 home area, probes/allocates `0x62B0` bytes, pushes RCX, then replaces RCX with the `.xpdata` address `0x1432A5455` before jumping to `0x145B1E769`. The second pushes RSI/RDI, probes/allocates `0x5A88` bytes, pushes RCX, then replaces RCX with `.xpdata` address `0x1432A2FF6` before jumping to `0x145B8EEEA`. The stack-probe callees are the previously identified page-touching helpers, not transform routines.

The callback inputs are two adjacent binary regions: `0x1432C1CDD + 0x3C = 0x1432C1D19`, and `0x1432C1D19 + 0x36 = 0x1432C1D4F`, the callback's entry. A read-only comparison of all 114 bytes found the live process matches the on-disk image exactly. The data is not readable text, and its role is unknown; the lengths do not by themselves identify it as a key, IV, or transform payload.

These two `.xpdata` addresses are dispatcher seeds passed as data in RCX, not Ghidra-recognized functions; neither lies in a `.pdata` runtime-function range. Their 64-byte live windows matched the on-disk image. The first seed starts with `MOV [RAX+RDI],EDX; JMP 0x1432AF92E`; it also has a direct incoming JMP from `0x1432AAAF0`, which is reachable in helper 2's decoded closure but not helper 1's current direct-flow closure. The second seed begins with a short jump/push/jump sequence and includes a separate zero-return stub plus pointer data. The direct-flow graph from the seed bytes is not yet fully resolved, so they remain seed labels rather than function names.

Following only Ghidra-decoded direct branches from those entries reveals a flattened/opaque graph rather than a clean linear decoder:

- First helper path begins `0x1432BB419 -> 0x145B1E769 -> 0x145A5A516 -> 0x145CA3D9E -> 0x145A8FEC0 -> 0x145A4315A -> 0x145A4049B`. At `0x145A4049B`, a conditional `JNZ` selects `0x145A3A74C`; the fallthrough path pushes RAX and jumps to `0x1432B596B`. The branch condition depends on prior state, so static linear disassembly alone cannot determine which route runs.
- Second helper path begins `0x1432A8647 -> 0x145B8EEEA -> 0x145D3EE2C -> 0x145D0954D -> 0x145A98F45 -> 0x1432ABE30 -> 0x145A36B64 -> 0x145A3BA55`, and the direct-flow walk now reaches `0x1432AEE2C -> 0x1432AEE30 -> 0x1432AEE37`. The last two instructions are `XOR RCX, 0xECBE66F4; JMP RCX`.

Both roots terminate their direct-flow walk at register-decoded indirect jumps. The first reaches `0x1432A957C -> 0x145A42A50 -> 0x145A42A53`, where the last two instructions are `BSWAP RDX; JMP RDX`. The second reaches `0x1432AEE30 -> 0x1432AEE37`, where it XOR-decodes RCX before jumping. The exact dispatch instruction bytes at both sites match the running process and on-disk Ghidra image in the 2026-10-31 read-only comparison.

Ghidra currently associates 81 `COMPUTED_JUMP` destination references with each dispatch site. The two 81-address sets are disjoint. These are candidate edges stored in the Ghidra database, not proof that each destination is selected at runtime. A bounded walk from the 81 candidates in each set through existing direct branches in `.xpdata` reaches 3,021 and 3,006 distinct listed instruction addresses, respectively, with 626 addresses shared; each closure also contains the same 13 computed-jump sites and one distinct computed-call site. The best-supported current model is therefore mixed: `.pdata`-registered function bodies can be transformed in place, while the observed startup dispatch fragments are unregistered, remain unchanged at their candidate entries, and route through encoded indirect branches. A uniform “decrypt all of `.xpdata` once” explanation does not fit these observations. Timing and behavior of the transform still need a runtime trace.

Many adjacent bytes decode as alternative short blocks, pushes, conditional branches, or indirect transfers; they are not all sequential instructions. This is evidence of hostile-to-linear-disassembly control flow, not proof of a VM or a custom calling convention. The wrapper boundary is consistent with the normal Windows x64 ABI, while the interior remains unexplained. The next useful trace unit is each reachable basic block and its incoming branch/state—not every byte in the 69 MiB section. A dynamic instruction trace or breakpoint-assisted single-step at the branch hub would resolve paths that file disassembly cannot.

A public Havok-derived header documents `hkpContactListener` with contact-point and collision callbacks, a virtual destructor, and contact-added/removed callbacks. That header is useful as a slot-order hypothesis only: it is not the Mad Max 2013.2 SDK header, and the Mad Max table appears to have seven slots rather than the later eight-slot layout that includes `ContactProcessCallback`. Do not assign the callback name/signature to slot 0 in the Rust ABI until the exact Mad Max version or its call site is independently confirmed. This comparison does, however, prove that the breakable-tree handler is wired to Havok's contact-listener interface, not merely carrying an unrelated RTTI base name.

These findings sharpen the next investigation into three separate questions: (1) whether `CMapStreamer`/`CStreamPatchManager` consume the world manifest and `.fl.mdic` placement arrays; (2) whether vegetation patch handlers can serve as a game-owned live physics-object lifecycle example; and (3) whether the general `CGameObject` creator route can reuse authored `.ee` or `worlddecorations.bin` compositions. The likely first reversible experiment should still be a game-owned spawn of a known rigid asset, while arbitrary landscape removal remains a separate streaming/save-state problem.

### Newly identified encoded dispatch pool J

The previously unlisted route from `0x1432ABEDD` is now decoded through to its indirect dispatch. `0x1432AAD9C` contains `CMC; XOR RCX, 0xFFFFFFFFDADBE5BA; JMP RCX`. ### Register-state evidence at the Pool J boundary

The six known A–I fragments that enter `0x1432ABEDD` share a striking boundary pattern: each loads `ESI` from `[RBP]`, advances `RBP` by eight, and jumps to the same setup block. The setup then adjusts `RSI`, reads a byte from `[RSI]`, advances `RSI`, transforms the byte, and uses it to select a table slot. This makes `RSI` a strong candidate for an encoded byte-stream cursor and `RBP` a candidate for a virtual stack/state cursor at this boundary. The exact values and global meanings remain unknown; in particular, the 32-bit `ESI` load and later arithmetic mean we should not treat the observed value as a plain host pointer.

Across the 81 J candidate fragments, a non-mutating block decode found RSI-family instructions in 32 fragments and RBP-family instructions in 62; 21 mention both. The inventory contains 18 RSI-relative memory reads, 95 RBP-relative memory reads, seven RSI adjustments, and 40 RBP adjustments. RSI reads include byte, word, dword, and qword widths; RBP accesses also use mixed widths and offsets, and at least one fragment writes a value back to `[RBP]` after moving the pointer by eight. For example, fragment `0x1432B4F5C` reads `[RSI]` and `[RBP]`, advances RSI by one and RBP by two, then jumps to another shared block. These varied widths and writes fit a virtual instruction cursor plus operand/state stack better than a simple fixed-width argument list, but they do not prove one uniform register convention. The instruction-level inventory is [`startup-pool-j-state-register-uses-2026-10-31.tsv`](startup-pool-j-state-register-uses-2026-10-31.tsv).

The same register survey across the earlier 729 candidates in pools A–I shows the pattern is not unique to J: each pool has 24–34 fragments mentioning RSI-family registers and 56–65 mentioning RBP-family registers; 10–21 fragments per pool mention both. Each pool also has 15–20 RSI-relative memory instructions and 82–95 RBP-relative memory instructions. The per-pool counts are in [`startup-dispatch-pool-register-summary-2026-10-31.tsv`](startup-dispatch-pool-register-summary-2026-10-31.tsv). This consistency across all ten pools strengthens the shared dispatcher-state interpretation, while exact register roles and data layouts remain unproven.

This discovery corrects the earlier nine-pool picture: the ten-root graph's `0x1432ABEDD` path leads to pool J, rather than ending at an undecoded gap. There are now at least ten distinct 81-target dispatch pools in this startup region. The 43-edge strongly connected component result remains specifically about the earlier A–I subset; J needs a full transition pass before making a connectivity claim across all ten pools. ### Pool J junk-code and liveness spot-check

The candidate fragments do contain concrete obfuscation-like noise, but the examples also show why “this whole block is junk” is too strong without control-flow and dataflow checks. In candidate `0x1432C04A2`, `CMP EBP, EBP` at `0x1432C04B9` sets flags that are overwritten by `TEST DX, DI`, `CMP CX, SP`, and `TEST SI, BX` before the fragment's unconditional jump. Its flag result is therefore dead on this path. Candidate `0x1432BFF0E` executes `BSWAP ESI` at `0x1432BFF95` and again at `0x1432BFFB9` with no intervening write to ESI, so the pair has no net effect on ESI's final value. Candidate `0x145A3E486` runs `DEC SI; BSWAP ESI; RCL SI, 1` immediately before `MOV ESI, [RBP]`; the full register overwrite and unconditional exit make that transformed value and its local flag effects dead on this path. These provide several strong, instruction-local dead-code examples, not proof that their surrounding candidate fragments are wholly dead.

The same `0x1432BFF0E` fragment also contains conditional branches and instructions such as `MOV RSP, RBP`, `SBB RBP, RDX`, and `POP RBP`. Those alter control flow or stack/register state and cannot be dismissed merely because the neighboring arithmetic looks absurd. The useful working model is a mixture: provably dead instructions, opaque or obfuscated control flow, and state-changing operations whose roles remain unknown. The bounded, instruction-specific findings are recorded in [`startup-pool-j-obfuscation-audit-2026-10-31.tsv`](startup-pool-j-obfuscation-audit-2026-10-31.tsv). This supports filtering dead calculations by flag/register liveness during future analysis; it does not establish that the entire protected dispatch region is a conventional virtual machine or that every candidate executes.

### RBP-relative operand updates across dispatch pools A–J

A listing scan of the 729 A–I candidates finds 32 fragments with an RBP-relative memory destination or read-modify-write instruction, spread across every pool (two to five fragments per pool). Examples show a repeated operand-update shape amid unrelated instructions: `0x1432A95DA` loads a qword from `[RBP]` and adds it to `[RBP+8]`; `0x145A47691` loads a word from `[RBP]`, subtracts six from RBP, then adds AX into `[RBP+8]`; `0x1432B1140` loads a dword from `[RBP]`, subtracts four, then ANDs EAX into `[RBP+8]`. After pointer adjustment, the write destination is at the original RBP plus two or four bytes, respectively. The byte/word/dword/qword widths and offsets vary, so this looks like packed typed operands or a virtual state stack, but that interpretation remains a hypothesis. The per-pool candidate counts are in [`startup-dispatch-pool-rbp-write-summary-2026-10-31.tsv`](startup-dispatch-pool-rbp-write-summary-2026-10-31.tsv); they are a static listing scan, not runtime frequency or proof that every candidate executes.

A closer comparison of 25 observed binary read-modify-write examples across pools A–J finds a precise normalization: the fragment loads operand A from `[RBP]`, adjusts RBP by `stride - 8`, then applies ADD or AND at `[RBP+8]`; in the original coordinate system, that destination is `[initial RBP + stride]`. The observed strides are 2 bytes for byte/word operations (RBP delta -6), 4 for dword operations (delta -4), and 8 for qword operations (delta 0). All 23 A–I examples fit, and two independently decoded Pool J examples fit the same relation. It is consistent with an interpreter operation over adjacent, width-dependent operands, with byte values occupying at least a two-byte stride. It does not yet reveal why RBP is represented this way, whether each slot contains tags or padding, or whether the adjustment is an operation-level stack pop. The complete normalized rows are in [`startup-dispatch-pool-rbp-binary-op-shapes-2026-10-31.tsv`](startup-dispatch-pool-rbp-binary-op-shapes-2026-10-31.tsv).

The six A–I memory-AND cases, plus one independently observed Pool J case, are more specifically AND-NOT patterns: each first applies `NOT` to the value at `[RBP]`, then loads its low operand-width bits into a register, and finally applies `AND` to the adjacent destination. For the observed width, this computes `destination &= ~source` (a bit-clear operation), not plain `destination &= source`; in a few cases the memory NOT is wider than the later register load, but the low bits used by AND are still the complemented source bits. The NOT does not set flags; the final AND supplies the flags consumed by any immediately following conditional branch. This is a useful first semantic opcode family to emulate in a future static interpreter model.

Pool J also has explicit stores that are absent from the A–I write scan. Two candidates subtract six from RBP and, on a surviving branch path, write AX to `[RBP+8]`, which resolves to the original `[RBP+2]`; another saves the previous RBP value, subtracts eight, and conditionally stores that saved value at the new `[RBP]`. These look like narrow value movement and a pointer/frame-like save within the same state area, but the branch predicates and surrounding operations leave their high-level purposes uncertain. The exact bounded sequences and caveats are in [`startup-pool-j-rbp-write-shapes-2026-10-31.tsv`](startup-pool-j-rbp-write-shapes-2026-10-31.tsv).

All 25 observed fragments transfer immediately after the memory update: six use a conditional jump and 19 an unconditional jump. In the conditional examples the operation's flags are directly consumed: ADD→JNZ, ADD→JL/JGE, and AND-NOT→JBE/JLE/JA. For the AND-NOT cases, the final x86 AND flags make these branch conditions correspond to zero/nonzero or signed-result status (AND clears CF and OF). This is stronger evidence that the repeated ADD/AND-NOT sequences are meaningful typed operations rather than random noisy arithmetic; conditional variants also appear to use the resulting flags as virtual control flow. The six examples and totals are captured in [`startup-dispatch-pool-rbp-binary-op-branches-2026-10-31.tsv`](startup-dispatch-pool-rbp-binary-op-branches-2026-10-31.tsv). This still does not identify the dispatch selector or prove a complete bytecode/runtime model.
