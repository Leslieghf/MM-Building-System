## Relevant public modding evidence

### Existing entity spawner

The [EntitySpawner Nexus page](https://www.nexusmods.com/madmax/mods/101) describes version 0.1 (uploaded 2024-08-31), claims Steam and GOG support, and advertises spawning vehicles, characters, encounters, and other game entities. It requires the [Ultimate ASI Loader](https://github.com/ThirteenAG/Ultimate-ASI-Loader) and says to put the plugin under `scripts` and open its menu with `/`.

This materially improves feasibility: in-process object creation has at least been attempted by a community plugin. The public description does not prove static structure placement, safe cleanup, persistence, or compatibility with this exact executable hash. Public comments include both reports that it still works and reports that the menu does not appear, so its reliability is uncertain. The author’s permissions restrict modification and redistribution; treat the published file as a black-box test/reference only. Do not copy its code, assets, or binaries into our project.

### Console command route (not available natively in the user's game)

The user checked the game and confirmed there is no built-in Gameplay console setting. The [Mad Max command console Nexus page](https://www.nexusmods.com/madmax/mods/43) describes version 1.2.1, updated 2023-06-25; its author says the tool injects a thread and calls commands already present in the game, and comments say to launch the game first and then start the console tool. This remains a possible third-party probe, but it is closed source and runs with game-process access. The Nexus “safe to use” label is not equivalent to source review or a guarantee; no file was downloaded or executed. It is not a native feature or a ScriptHook API, and installation/use would need a separate review.

A [Steam Community command list](https://steamcommunity.com/sharedfiles/filedetails/?id=3446023886) includes `Spawn <Entity> <Amount>` and prop identifiers such as `treeprop`, but its metadata is mismatched and the user confirms the described built-in console option is absent. Treat the command syntax and IDs as unverified; they cannot guide an experiment until corroborated from the game data or an inspected tool. Do not use them against the main save.

### What an ASI loader does (and does not do)

The [Ultimate ASI Loader documentation](https://github.com/ThirteenAG/Ultimate-ASI-Loader) describes a proxy DLL that loads `.asi` modules and calls an exported `InitializeASI` entrypoint. It supports several DLL names imported by this exact executable. That gives our code a way to load inside the game process; it does not provide game functions, object handles, a safe game-thread queue, world lifecycle events, or a ready-made scripting API. Existing Mad Max runtime mods implement their own signatures/hooks and game-specific calls. For example, [Wasteland Storms](https://www.nexusmods.com/madmax/mods/212) uses the loader and MinHook; its page says GOG is tested and Steam is untested, and the described Steam path scans for functions. That is not proof that its hooks or loader setup can be reused for construction.

The ScriptHook-like system the project wants would therefore be our own small game-specific API layered over those hooks. It could later offer safe, copied operations such as reporting area state or requesting a validated spawn, then host mod logic in Rust/Bevy. The loader is only the bootstrap. Rust can produce Windows DLLs and export a stable external entrypoint, but the game's internal function calls still need build-specific reverse engineering and unsafe FFI; doing that in Rust does not make it intrinsically safe. The current plugin proves only loader initialization, overlay rendering, and hotkey delivery.

### Local save identity evidence

The save-format project documents header offset `0x18` as a Unix playthrough-creation timestamp and `0x48` as the slot number; it reports measurements across 51 saves. I decoded only the first 0x50 bytes of this PC’s save files using that published XOR key and checked the documented magic/fields. Four occupied Steam slots (1, 2, 3, 10) have distinct creation timestamps; both available Documents backups (slots 1 and 2) match their corresponding Steam copies. This suggests the creation timestamp can distinguish the currently observed playthroughs, with slot number as a second field. It is a small local sample, not proof against timestamp collisions or altered/corrupt saves. We have not established a supported way for a runtime bridge to identify the currently active save/slot without observing game state. For the prototype, use explicit profile selection until active-slot identification is demonstrated; never infer the current profile merely from the newest save file.

### Hook and loader precedents

- [MadMaxFix](https://github.com/Alexxlml/MadMaxFix) documents tested Steam 2015-10-22 and GOG 2015-12-01 builds. Its [source](https://raw.githubusercontent.com/Alexxlml/MadMaxFix/main/src/fix.c) checks PE timestamp 0x5628A448, verifies function bytes before installing MinHook hooks, and on Steam waits for the decrypted code to match before proceeding. It is a drop-in XInput9_1_0.dll proxy; the source says Mad Max imports only XInputGetState and XInputSetState. This is an alternative to an ASI loader for our own bridge, though the proxy filename conflicts with MadMaxFix and any other mod using it. Its private hook functions do not establish a general game API.
- [MadMaxCrashFix](https://github.com/x0reaxeax/MadMaxCrashFix) documents `dinput8.dll`, `dxgi.dll`, and `XInput9_1_0.dll` variants and executable-specific reverse engineering. This shows several possible proxy names already have community usage/conflicts.
- [Ultimate ASI Loader](https://github.com/ThirteenAG/Ultimate-ASI-Loader) supports multiple proxy DLL names, including `dinput8.dll`, `dxgi.dll`, `xinput9_1_0.dll`, and `bink2w64.dll`. For the Bink proxy it requires preserving/renaming the original DLL. Loader choice must therefore account for already-used proxies and a clear rollback path; do not install it by blindly copying a DLL into the game folder.
- The [Mad Max save editor’s format notes](https://github.com/Rick-Thompson/MadMax_Savegame_Editor_Project/blob/main/docs/FORMAT.md) report in-game verified restoration of destroyed static props and cleared convoys through save editing. Its [game-file notes](https://github.com/Rick-Thompson/MadMax_Savegame_Editor_Project/blob/main/docs/GAME-FILES.md) explain how game data relates to save records, while also identifying unresolved camp state. This is evidence for restoration of native saved objects, not proof of arbitrary runtime spawning or our chosen sidecar model. This project identifies scarecrows as a static-prop example (roster type 45) restored through existing save state; that is a useful research target but not an arbitrary placement or runtime-spawn recipe.

### Player-position probe candidate (research only; not installed)

- The user rejected the display-mode-count hook as too weak a game-facing milestone and requested a real player-position readout, gated to a point where gameplay is active.
- Wasteland Storms' public source hooks `CPlayer::UpdateController(void* thiz, float dt)` and runs its update logic there. Its comments report that this callback also runs in menus, while game-weather data becomes available only after the open world loads. This is a useful game-specific callback lead, but its documented byte pattern comes from a GOG build and its Steam support remains unconfirmed. It does not read or document player coordinates.
- The Steam executable timestamp matches MadMaxFix, but that is not evidence that the GOG callback signature matches Steam. The local executable's unusual section layout also means a `.text`-only scan is unsuitable. Any candidate must locate the callback in the live image using a uniquely matching, validated pattern or a separately verified fixed address, then refuse to hook otherwise.
- The `this` pointer to `CPlayer::UpdateController` may provide a route to player state, but no verified transform field, coordinate convention, object lifetime, or world-ready gate has been established from the sources examined. Do not read a guessed offset or label an arbitrary float triple as position.
- The user's requirement is a normal mod experience with no Cheat Engine setup or dependency. Do not use Cheat Engine tables or workflows as research inputs. Find the callback and transform through public mod source and read-only inspection of the exact Steam executable/runtime behavior, and validate any candidate inside our own plugin only after source review.
- A recent public M4 multiplayer update from Reddit user `u/VespucciBoy` says the author located the host's position and transform, and an earlier post says Max's transform/world-position data was being indexed. A later update reports stable guest tracking. This is strong evidence that position access has been achieved in at least one Mad Max setup, but the posts do not disclose the address, structure layout, callback, executable distribution/hash, or source code. Treat it as a community lead, not a verified adapter contract. Do not contact or message the author without the user's explicit authorization.
- The current public [Wasteland Storms source](https://github.com/PabloCGSilva/MadMax-WastelandStorms/blob/main/storms.cpp) confirms its GOG-derived `CPlayer::UpdateController` signature, and shows that it scans only a `.text` section. It hooks `GetStartupInfoW` to retry after Steam startup/decryption, but still declines to proceed if it cannot find `.text`; because the user's Steam executable has no `.text` section, this source is not by itself a demonstrated Steam callback route. The user's current working prototype already has an in-game rendering/hotkey path, so next research should focus narrowly on obtaining evidence for the player data and a compatible callback, not adding another rendering stack.
- Next research step: derive and independently validate the Steam player-transform source/field using public source and static analysis of the target executable. If that cannot establish a stable field, prepare a deliberately bounded, user-reviewed in-plugin diagnostic spike that correlates candidate values in a disposable context. Keep it read-only, avoid third-party memory tools, and do not install or run it until the user reviews the complete Rust diff. Only then add a live overlay readout, with stale data hidden outside confirmed gameplay.

### Recent ecosystem evidence (September–October 2026)

- The Nexus Mad Max catalog now includes 2026 runtime mods beyond simple data replacements. [Enhanced Convoy](https://www.nexusmods.com/madmax/mods/210) documents detecting destroyed convoy state, waiting until the game finishes wreck handling, respawning the convoy after a timer and distance condition, and writing a diagnostic log. Its beta also explicitly reports the Steam difficulty: logs from Steam users show no `.text` section and no signatures found. The author changed scan behavior, but the latest page still marks Steam support unconfirmed.
- [Wasteland Storms](https://www.nexusmods.com/madmax/mods/212) documents reading weather state, distinguishing open world from strongholds/interiors/camps/tunnels, calling the game’s native storm command, showing text in the game’s UI font, storing settings in an INI, and not changing save files. The page says GOG is tested and Steam should work but remains unconfirmed.
- [Enhanced Archangels](https://www.nexusmods.com/madmax/mods/213) expands game tables/UI beyond a vanilla 16-item limit, combines runtime hooks with `dropzone` data changes, and refuses unsupported executables. It lists Steam as untested. Together these mods show the practical ecosystem is moving toward paired native data edits plus small in-process ASI hooks, with logs and build checks.
- Your on-disk Steam executable’s PE section names are `.bss`, `.data1`, `.data`, `.pdata`, `.reloc`, `.trace`, `.xcode`, `.sbss`, `.xpdata`, and `.xtext`; there is no `.text`. The large `.xpdata` range and small `.xtext` range are recorded from the PE header only. This explains why a mod that specifically scans the executable for a `.text` section can reject the Steam file. It does not establish how Steam decrypts or maps code at runtime.
- [MadMaxFix’s source](https://raw.githubusercontent.com/Alexxlml/MadMaxFix/main/src/fix.c) takes a different route for Steam 2015-10-22: it checks the PE timestamp, uses known function addresses for that build, waits until the expected code bytes appear in memory, then checks all hook bytes before installing. Your timestamp is an exact match. This is a strong precedent for a fixed-build bridge, but it does not provide the construction-spawn API or prove that its addresses apply to the function(s) we need.
- [Mad Manager](https://github.com/y0xOFF/Mad-Manager) covers installation of `dropzone` mods and does not solve runtime APIs. [EntitySpawner](https://www.nexusmods.com/madmax/mods/101) remains a separate black-box runtime-spawn precedent requiring Ultimate ASI Loader. The recently active community also includes ambitious multiplayer research, but that is not a dependency for our building slice.

|---|---|---|

| Area-ready event and safe game thread | Recent mods detect open-world/interior/weather state and wait for game-state conditions, but public descriptions do not specify callback thread or reusable lifecycle hook | Partially evidenced behavior; safe callback/thread contract not proven |
| Active playthrough identity for sidecar | Save header 0x18 is documented as a Unix timestamp for playthrough creation and 0x48 as slot number; local inspection found distinct keys across four occupied Steam slots and matching keys in available slot backups | Good candidate key for a selected profile; active-slot discovery is still unsolved. Require explicit profile selection until runtime detection is proven; collisions remain theoretically possible. This is sufficient to close the identity investigation for the first profile-selection design, not to claim automatic detection |
| Rust bridge feasibility | Rust toolchain and reviewed ASI bootstrap already exist; game callback/transform ABI remains unknown | Bootstrap/render path proven; game-facing read capability not assessed |

**Decision:** Keep the installed hotkey/overlay build as the safe baseline. Do not yet add a game-data read or replace the installed ASI. The next Rust change must follow evidence for a Steam-compatible callback and transform, then be shown to the user line by line before installation. Construction feasibility is a separate gate: this position milestone does not establish safe object spawn/removal or persistence. ASI loading gives us an in-process entrypoint, not a ready-made game API.
