# Scripted Spawn Workbench and World Tools — Design

**Status:** Recommended project direction; first slice is bounded script-owned spawning and a verified asset catalog.
**Date:** 2026-10-31

## Intent

Grow the current Mad Max bridge into a modder-facing world-tools foundation: a GMod-inspired spawn browser, script-owned placement and ray configuration, a catalog of shipped entities, and eventually a selection/removal tool. The experience should feel scriptable and extensible without asking every modder to call raw native addresses or duplicate the same UI/raycast glue.

## What exists today

- The native overlay has a hold-Q spawn menu and can place a verified small scrap-stockpile entity using a ray result copied from the game. Q currently causes whole-input focus capture, which blocks movement while open.
- Rhai callbacks can independently request bounded raycasts, draw debug gizmos, publish small UI panels, read mod-owned input, and hot-reload packages.
- The native game adapter can submit entity spawn requests and now has a candidate game-owned despawn call for identities generated by the spawn system. Removal has not yet been verified in-game.
- Package discovery/compilation currently centers on a `main.rhai` entry source. There is no script-visible spawn request API, no general asset catalog, and no package-local multi-file source loader.
- Available source evidence includes entity keys and definitions from community work and local archive inspection. These data sources contain compositions with gameplay behavior as well as simple-looking props; an `.ee` filename alone does not prove it is a standalone prop or safe spawn target.

## Goals

1. Make one single-file `debug_spawn_menu` package own the spawn menu's placement ray, hit marker, settings, and spawn UI; use R as the initial toggle.
2. Add a typed, capability-gated `ctx.entities` API that accepts only catalogued spawn entries and finite placement transforms; keep every native call in the existing game callback adapter.
3. Build an evidence-tagged catalog that grows from discovered game assets, with user-facing folders and names plus separate asset kind, motion behavior, confidence, and spawn readiness.
4. Keep this first application in one `main.rhai` file; consider bounded multi-file packages later if the workbench grows enough to justify loader changes.
5. Establish an in-game tool mode that can remove an entity only when its exact mod-owned native spawn identity is known and removal has been validated.
6. Investigate arbitrary map-object removal and a native custom weapon/slot as separate research tracks, promoting them only when object identity, lifecycle, and registration contracts are known.

## Non-goals and anti-goals

- Do not directly allocate Havok bodies or fabricate physics/material data while the game-owned entity path remains available.
- Do not claim that every archive key is an individual prop, or that `static` is synonymous with `prop`.
- Do not allow arbitrary asset strings, native pointers, or object addresses from Rhai.
- Do not delete a map-authored object based solely on a ray hit position.
- Do not add a weapon slot just to get a Toolgun-shaped UI into the game. A script-owned tool mode can establish the behavior first.
- Do not make a single mandatory giant package that blocks unrelated mod scripts.

## Approaches considered

### Native spawn menu and native tool implementations

This keeps current actions straightforward, but every new panel and interaction becomes Rust overlay code and cannot be hot-reloaded by modders. It remains appropriate for critical host controls and safe input ownership.

### Script-owned workbench over bounded native capabilities — selected

Keep the platform layer responsible for package lifecycle, input capture, copied snapshots, bounded panels, catalog validation, and game callback execution. Let a package orchestrate raycasts, gizmos, UI and spawn intents through typed effects. This fits the existing Rhai/ECS architecture and gives modders useful behavior without exposing raw ABI calls.

### Native Toolgun weapon and unrestricted world mutation

This could eventually feel most like a game-native tool, but it needs weapon registration/slot semantics, assets/animations, input integration, object selection identity, and safe world lifecycle handling. RTTI and weapon-related strings (`CWeapon`, `CWeaponHolder`, `WEAPON_TYPE_RAYCASTGUN`, `WEAPON_TYPE_GRAVITYGUN`, `WEAPON_TYPE_TWEAKERGUN`) are investigation leads, not evidence that adding a weapon slot is supported. Do not make it the first implementation route.

## Input boundary

There are two different input concerns and they must have different names and contracts:

- **Mod-runtime input** is key state observed by the Rust/ImGui host and copied to scripts as `ctx.input`. It is not a query of Mad Max's controller map or native input state. The current general sampler is disabled, so `input.read` must not be treated as fully reliable until an event-driven sampling route is restored and verified.
- **Mad Max native input suppression** means preventing a game input event from reaching its normal handler. Hudhook processes queued messages asynchronously; its per-message break stops ImGui handling but not the already-forwarded game event. Overlay capture can suppress whole input categories. That does not yet demonstrate selective keyboard, mouse, XInput/controller, or weapon-action suppression.

Keep these as separate API surfaces: `ctx.input` for mod-runtime input and (only when implemented) `ctx.native_input` for an explicit native-input suppression request. Do not expose “read native key state” because no such mapping has been established. A suppression API should state whether it covers Win32 key messages, mouse messages, or the game's controller path. The target interaction is an R-activated workbench that keeps movement and camera aim live while only its own tool actions are consumed. R must not ship as an activation key until its native side effect can be suppressed or proven harmless. F1 whole-input capture remains a temporary fallback for testing, not the desired workbench interaction.

## Proposed architecture

```text
`debug_spawn_menu` (`main.rhai`)
  ├─ UI panels and package-owned state
  ├─ game.raycast request/result (copied values)
  ├─ game.spawn request by catalog ID and transform
  ├─ debug gizmos and mod-owned input
  └─ lifecycle/outcome events
          │ bounded, typed, generation-attributed effects
          ▼
Bevy ECS runtime and catalog validator
          │ accepted intents only
          ▼
exclusive Mad Max callback → game-owned spawn/despawn/query APIs
```

Scripts orchestrate capabilities; they never call the game or hold game pointers. UI panels and raycast state belong to the single-file `debug_spawn_menu` package. Host-owned input capture must recover safely on focus loss and script unload. Spawn requests use stable catalog IDs rather than raw `.ee` paths. Native results are surfaced as queued/submitted/observed/failed and do not call submission success “spawned.”

## Catalog contract

Catalog data is source-controlled and generated/curated from named asset sources. Each entry records:

- stable catalog ID, display label, and GMod-like category path;
- exact exported entity key and source provenance;
- content kind (`prop`, `vehicle`, `character`, `encounter`, `effect`, or `unknown`);
- observed physical behavior (`unknown`, `fixed`, `keyframed`, `dynamic`, or `not_physical`);
- evidence level (`name_only`, `archive_found`, `definition_inspected`, `spawn_observed`);
- spawn readiness (`blocked`, `candidate`, `verified`) and concise caveats.

Unknowns stay explicit. An item is selectable only when its entry is `verified` for the current game build. The database may include non-spawnable compositions so the browser doubles as a useful asset index without risking accidental calls.

## Toolgun direction

First deliver a script-owned “Tool” mode in the same workbench: choose a tool action, aim using a verified ray profile, and act on an object only if the adapter returns a validated game identity. Initially, allow removal only for identities created and tracked by this mod. Arbitrary map deletion remains disabled until research establishes how ray queries yield `CGameObject` identity, how streamed objects are owned, and what removal does across reload/save/zone transitions.

A true custom weapon slot is a later feasibility decision. Before implementing it, trace `CWeaponHolder`/`CWeaponSequencer` registration and enumeration, identify whether weapon type tables are fixed or data-driven, and verify the required asset/animation/UI registration path. If the game exposes no supported insertion path, keep the tool as a runtime-owned mode rather than forcing a fragile weapon injection.

## Phases and exit criteria

### Phase 0 — Existing foundation and catalog schema

Record the current feature boundary, introduce a machine-readable catalog format, and seed it with only evidence-backed keys. **Exit:** catalog entries distinguish inspected compositions from verified spawnables; the existing stockpile is identified as the first in-game verified entry.

### Phase 1 — Input route and weapon HUD discovery

Trace `CKeyboardRouter`, DirectInput/XInput acquisition, and a keyboard action through its native owner. Find the weapon selection HUD/control state and how it is hidden/updated. **Exit:** a tested way to observe mod keys independently from native action suppression, with clear input categories and no claim of per-key support until proven.

### Phase 2 — Script spawn effects

Add a typed script spawn intent. Validate catalog ID, capability, transform, queue capacity, and script generation. Route through the existing exclusive game callback and report outcomes to the requesting package. **Exit:** the single-file `debug_spawn_menu` package can request the existing stockpile by ID and receives truthful lifecycle results.

### Phase 3 — `debug_spawn_menu` Spawn Workbench

Move the menu content, its own player-aim raycast, optional hit gizmos, ray settings, and catalog selection into the package. Activate with R only after phase 1 proves it can avoid the game's native action; keep minimal focus/capture recovery in native host code. Replace the old native item grid only after parity is reached. **Exit:** the package does not depend on `reticle_ray`, can hot reload, allows movement/aim while open, and sends green verified or yellow unverified catalog IDs through the generic spawn attempt route; red entries have no usable spawn path.

### Phase 4 — Catalog discovery and browser

Ingest community catalogs and local archive/file-list data; deduplicate exact keys; inspect entity definitions/resources; provide search, folders, item tiles, and provenance. Keep confidence and spawn readiness visible in tooling/research. **Exit:** every exposed tile has a stable key, accurate category, and a reviewed readiness classification.

### Phase 5 — Owned-object Tool mode

Validate native despawn and lifecycle observation in-game. Add a script-owned selection/removal mode for tracked mod-created objects, with explicit selection and undo/recovery behavior where possible. Separately verify which keyboard messages can be swallowed without relying on Mad Max's native mapping; add a distinct `ctx.native_input` suppression capability only after that contract is demonstrated. **Exit:** repeated spawn/remove does not target map-authored objects or leave untracked entities in tested transitions.

### Phase 6 — Map-authored object identity/removal

Trace ray query result identity, `CGameObject` ownership/registration, map streaming, and persistence/save behavior. Implement only when selection can resolve a stable object identity and the game has a safe removal lifecycle. **Exit:** test removal and zone reload behavior are understood; any save mutation is opt-in and backed up.

### Phase 7 — Entity types and native Toolgun feasibility

Expand verified catalog entries to dynamic props, vehicles, NPCs, and authored compositions. Separately investigate weapon registration and decide whether a true weapon slot can be added safely. **Exit:** each type has a tested creation contract and each Toolgun integration has a proven registration point or an explicit “runtime mode only” decision.

## Risks and operating limits

- Script-to-game effects are deferred and can become stale after hot reload; every request must carry package ID and generation and be dropped when stale.
- Entity definitions may contain triggers, graph scripts, loot, persistence, encounter behavior, and multiple objects. Classification must inspect composition, not infer from key names.
- Candidate despawn ABI was not yet confirmed in-game; keep it behind host/native safety gates and install only after Mad Max is closed.
- The catalog can grow much faster than reliable spawn coverage. Keep discovery and actionability as separate axes.
- A full embedded Bevy runtime inside Mad Max is not the modder API; Bevy remains the host adapter, Rhai packages remain the primary user extension surface.

## Current decision

Recommended first deliverable: establish a tested mod/native input boundary and weapon-HUD map, then add the bounded script-to-spawn effect path and move the menu, ray controls, and optional hit indicator into one `debug_spawn_menu/main.rhai` package. Use script-owned Tool mode for deletion experiments. Research native weapon insertion and arbitrary map-object deletion in parallel only when relevant code evidence is available; do not make either a prerequisite for the useful workbench.
